Distributed video streaming · Java 21 · Spring Boot

A video load balancer, measured against MinIO and nginx

Heimdall stores each video on a shard, replicates it, and serves every seek by fetching only the chunks it needs from the shard's replicas, switching nodes when one fails. Every algorithm in it is benchmarked, and the whole system is compared with MinIO, SeaweedFS and nginx.

How it works

Three kinds of service, each a separate process talking to the others over HTTP: a gateway, storage nodes acting as primaries or replicas, and MinIO for the bytes.

Routing by rendezvous hashing

Every video belongs to one primary. Rendezvous hashing keeps each primary within about 2% of an even share, and when a node joins or leaves, only that node's videos move.

Seeking without downloading

Videos are stored as 1 MiB chunks. A seek is an HTTP Range request, so the gateway fetches only the chunks that overlap the bytes the player asked for.

Replicas that share the reads

Primaries copy each upload to their replicas. Each read fetches its chunks in parallel across a configurable share of the replicas, and falls back to the next node, then the primary, when one fails.

Streaming end to end

Uploads and downloads pass through without ever being held in memory whole, so even a multi-gigabyte video costs about one chunk of memory at a time.

Routing: the measurement that changed the code

Heimdall first assigned videos to shards with a consistent-hash ring hashed by CRC-32. It passed every correctness test. Measured against eight alternatives, it spread videos the least evenly, so it was replaced with rendezvous hashing.

Why not jump hash? It's the fastest option and spreads keys evenly, but it numbers nodes by position. When any node except the last one fails, every node after it shifts down and nearly every video moves. Switch the cluster size above to 8 or 32 to see it.

Against real products

The same 64 MiB file, read with identical HTTP requests from Heimdall, from the MinIO it stores its chunks in, from SeaweedFS, and from nginx serving a plain file. Every response was checked byte for byte.

Where Heimdall's time goes

Most of the gap is one extra round trip at the start of every read. Before fetching any video, the gateway asks a storage node for the file's metadata, and that node reads it from MinIO. Metadata never changes after upload, so caching it in the gateway is the next improvement.

The rest is the design's trade-off. A 64 MiB file becomes 64 separate chunk requests, which is what lets different replicas serve different parts and lets each chunk fail over on its own.

All four systems ran on one 12-core machine together with the load generator. That penalises Heimdall's seven processes the most, so treat these as relative results.

Testing

Property-based tests check the algorithms across whole ranges of generated inputs instead of a few examples. End-to-end tests start a real cluster, stop real processes, and check the bytes that come back.
